# Ho-ObjectBuffer 规划：逐物体通道（身份 / 覆盖率 / 具名选择 / 逐物体辅助量）

> **名字已定：`Ho-ObjectBuffer`**（决策 12）。`Cryptomatte` 留给**另一个 feature**——它做的是"**纯值 → object → surface 的递进覆盖 + 合成 + 选区/导出**"（见 §1.6 与 `Ho-Cryptomatte_规划.md`）。

> 状态：**设计草案待拍**（§6）。
> 取代：`Ho-CharacterBuffer_规划.md` 的 feature 定位（CB 取消）、`Ho-Cryptomatte_占位.md`（其内容已并入本文与 Cryptomatte 规划）。
> 决策来源：**角色特化后处理留着，但它吃的东西不再是 CB，而是本 feature**；所有需要遮罩的后处理统一走这里。

## 0. 摘要与心智模型

**把它当成视频合成流里的"ID/遮罩层 + AOV 入口"。**

后处理 feature 不再各自去啃五张语义图、二十个 source，而是统一问它一句"**我要哪一块**"，拿回一张**带覆盖率的遮罩**。它同时是"**乱七八糟、没啥人用、但必须有**"的 RT 的登记入口——角色 ID、部件、头部骨骼方向、具名选择，以及以后任何这类东西。

一句话边界：**它回答"这是谁、占多少、我要抠哪一块"；几何在 GB，表面数值在 SB。**

## 1. 决策（草案）

| # | 决策 | 一句话后果 |
| --- | --- | --- |
| 1 | **取消 `Ho-CharacterBuffer`**，其机制整体并入本 feature | 身份 / 覆盖率 / 两级 palette / RSUV 索引 / 自建 MSAA / resolve ——**代码已经存在**（CB P1 落地的那批文件就是骨架，改名即可；**上一轮只删了文档、没删代码，选择层完好**）。`Ho-CharacterBuffer_规划.md` 保留作参考资料（§4 业界依据、MSAA 规则、覆盖率容量分析仍然有效） |
| 2 | **所有需要遮罩的后处理只吃本 feature** | 角色特化（眼透 / 发影 / 脸色 / 轮廓）、SSS、ScreenProcess、PLR 的**遮罩需求**全部改读这里。它们仍按需读 GB（几何门控）与 SB（表面数值），但**遮罩只有一个来源** |
| 3 | **角色 ID + 部件表沿用 CB 的两级 palette + RSUV 索引** | 角色 8 bit + 槽位 8 bit；表在 CPU、像素里只有索引；RSUV 不序列化 → 每次重建都要重写 |
| 4 | **头部骨骼 → 方向 RT**（本轮新增） | 面朝方向本来就是"一个法线/颜色值"，**输出成一张图**比让每个消费端在 C# 里逐相机算更省心。`faceBone` + 三轴仍留在组件上、`TryGetWorldFacing()` 保留（C# 侧仍可用），但 **shader 侧改成按像素读这张图** |
| 5 | **具名选择（Cryptomatte 式）是本 feature 的核心能力**，不是附属通道 | 一张 RGBA8 装两个 `(ID, 覆盖率)` 对（`R=id0, G=cov0, B=id1, A=cov1`）。**命名纪律**：内部编码不合规时不许冒用 Cryptomatte 这个名字；**导出两档**：Deep IDs 的 UINT 通道 / 合规的 `crypto_*`（float 位重解释 + manifest + 32 bit） |
| 6 | **身份 + 覆盖率 = 自建 MSAA + 逐样本投票** | 相机把 AA 关掉也照跑（这正是最初那个 bug 的场景）；`K = N = 4` ⇒ 无尾部丢失 |
| 7 | **它是"乱七八糟 RT"的入口，但登记有规矩** | 每个通道必须写明：生产端 / 消费端 / 编码 / 生命周期 / debug 视图；**没有消费者的不分配**。不是"什么都能塞"，而是"**必须有、又没别处可放**的，放这儿，并且登记" |
| 8 | **ID 不区分角色与场景：一个空间、一套表** | 角色的部件和场景物体**混在同一个 ID 空间里**；"这是什么区域、有什么属性"由 **palette 的类别 / 标签 / 属性**回答，而不是靠 ID 的高字节去分域。ID 仍是 `组 8 + 槽位 8`（高字节只用来做"**同一组**"的廉价比较，不再意味着"这是角色"）；表结构仍是两级（组表 → 条目表），但"组"是泛指的（一个角色、一组道具、一片场景区域） |
| 9 | **任何物体都能挂 ID 组件** | 组件不再叫"角色"什么——它是**通用的 ID 声明**（`HoObjectBufferGroup`）。谁要 ID、谁要能被抠出来，谁就挂它；不再有"这是角色专用 / 场景专用"的两套 |
| 10 | **具名选择每像素 8 个**（混合存储之后取安全值） | 角色与场景混存意味着一个像素里可能叠更多东西，所以按业界默认（Redshift 8 / Octane 6 / Psyop gizmo 12 槽）取 **8**。成本：一对 = ID 8 bit + 覆盖率 8 bit，8 对 = **16 B/px**（4 张 RGBA8），**按需分配**（没有选择条目就一张都不开） |
| 11 | **朝向要两张内容：forward + side**（叉乘得第三轴） | 消费端 `up = cross(forward, side)` 之类自己算，不必再传第三个向量。**打包：两个方向各用 octahedral 编码塞进同一张 RGBA8**（RG = forward、BA = side）——这就是"两张内容"，但只花 **4 B/px** 而不是两张纹理的 8 B/px（octahedral 编码法线是 UE/HDRP 的常规做法，见 CB 规划 §2.5 的引用）。**压缩是有损的**（极点附近误差更大），但朝向是**低频**量、只用来做角度类效果，8 bit 足够；真不够时把这张图升成 16F 即可，**消费端一行都不用改** |
| 12 | **命名分层：feature 不该叫 Cryptomatte** | 它装的不只是 ID（还有朝向这种逐物体辅助量），叫 Cryptomatte 会**承诺一个它不打算守的边界**，然后**邀请**一切"没别处可放"的东西搬进来——这正是垃圾场的成因。**建议改名 `Ho-ObjectBuffer`**（逐物体通道：身份 / 覆盖率 / 具名选择 / 逐物体辅助量），而 **`Cryptomatte` 只作为"选区语义 + 导出档位"的名字**（契约里的 `crypto_*` 档、UI 上"抠像/选区"的说法）。这样：**名字描述的是轴（逐物体），不是一个具体用途**——轴是稳定的，用途会不断长出来 |

## 1.5 准入规则：这个 feature 允许装什么（防垃圾场）

光有"登记制度"挡不住垃圾场——**得有一条能在 10 秒内判完的判据**。这里就是那条：

> **判据：这个量是「逐物体 / 逐区域」的吗？**
>
> - **是** → 可以进这里（身份、覆盖率、具名选择、朝向，以及以后同类的逐物体量）。
> - **不是（逐像素的材质数值）** → 去 `Ho-SurfaceBuffer`。
> - **不是（几何）** → 去 GB。
> - **不是（效果的调参意图）** → 它是**材质轻量参数**（管线草案 §6.3），留在材质侧。
> - **都不是** → 那它**该有自己的 feature**，就像 SB 那样被拆出去，而不是塞进来。

**允许的两类**：

| 类 | 例子 | 为什么属于这里 |
| --- | --- | --- |
| ① **身份** | 组/条目 ID、覆盖率、具名选择 | 逐样本/逐像素的"这是谁" |
| ② **逐物体辅助量** | 朝向（forward + side） | **逐物体**（整组一个值），既不是几何也不是表面数值，但每个像素都要读到 |

**明确拒绝的**（这些各有其家，写在这里免得下次又有人往里塞）：

- 表面色 / roughness / metallic / thickness / 曲率 / 反射参数 → **SB**；
- 法线（几何或着色）/ 深度 / 几何覆盖率 → **GB**；
- `giStrength` / `_SSAO*` / `gisexclude` / sss strength 这类**效果意图与调参** → 材质轻量参数或它们自己登记的通道；
- **逐像素**的任何材质量 → **SB**（判据那一条就能挡住）。

**并且加上限**：类②（逐物体辅助量）**最多两张图**。超了就得先回答"为什么它不能去 SB / 自己的 feature"——上限的作用不是省显存，而是**强制一次对话**。

**为什么把朝向放在这里而不是 SB**：它是**逐物体**的（整组一个方向），不是逐像素的表面数值。判据一致，所以它不构成"垃圾场"的先例——它是这条判据的第二个正例。

## 1.6 与 `Ho-Cryptomatte` 的分工：本 buffer 只管"提供可写通道"

`Ho-Cryptomatte` **不是**本 feature 的一部分，而是一个**合成层**：把三个来源按"**纯值 → object → surface**"的递进顺序**合成出一个能用的属性**，并由此产出遮罩 / 选区 / 导出。架构因此是三轴 + 一层合成：

```text
GB（几何轴）             ─┐
ObjectBuffer（逐物体轴） ─┼─→ Ho-Cryptomatte（递进覆盖 + 合成 + 选区/导出） ─→ 消费者
SurfaceBuffer（表面轴）  ─┘
```

**分工原则（这就是"更解耦"的落点）**：

| 谁 | 负责 | **不**负责 |
| --- | --- | --- |
| **各 buffer** | 产出自己那一轴的原始数据，**并预留若干可写通道**（留给材质 / 工具 / 艺术家写） | 不定义"多来源冲突时谁赢"，不解释属性语义 |
| **`Ho-Cryptomatte`** | 递进覆盖的**优先级与合成规则**、具名选区、manifest、导出档位、给消费者的统一入口 | 不自己画几何 / 表面（它读别人的图） |

**本 buffer 提供的可写通道** = §1.5 里"类② 逐物体辅助量"的槽位（**上限两张图**）：例如朝向那张 RGBA8（`RG=forward`、`BA=side`），以及将来登记进来的同轴量。**不用的图不分配。**

> 收益：**加一个新属性不必改本 feature 的契约**——只要它在"逐物体"这条轴上，就占一个可写槽位；至于它怎么被合成、消费者怎么读，由 `Ho-Cryptomatte` 定。

## 2. 消费者与输入

| 消费者 | 从本 feature 拿什么 | 还需要别的吗 |
| --- | --- | --- |
| **角色特化**（眼透 / 发影 / 脸色扩散 / 主体与增强轮廓） | 组 / 条目的 ID + 覆盖率 + 具名选择；**"同一组"用 ID 高字节廉价比较**（决策 8） | GB（几何门控） |
| **SSS** | "谁参与 SSS" 的遮罩（具名选择）+ 分类/profile | **SB**（thickness / curvature / 表面色）+ GB |
| **ScreenProcess** | **只吃具名遮罩 + 覆盖率**（今天 20 个 source → 1 族） | 材质意图仍在材质侧（管线草案 §6.3） |
| **PLR** | 反射平面 / 参与物体的遮罩 | GB + SB |
| **AOV / 导出** | ID + 覆盖率 + manifest（名字表） | — |

> 为什么这样更贴近心智模型：**它们本质都是"屏幕后期 + 遮罩"**，与视频合成流一致——先有 ID/遮罩层，再谈效果参数。而"表面是什么样"（SB）与"几何在哪"（GB）是另外两件事。

## 3. 通道（草案）

| 通道 | 格式 | 内容 | 分配 |
| --- | --- | --- | --- |
| `_HoCryptomatteId0` / `_HoCryptomatteId1` | RGBA8 | 4 层 `(组 8, 槽位 8)`——组既可以是角色也可以是场景区域，不区分 | 常开 |
| `_HoCryptomatteCoverage` | RGBA8 | 4 层覆盖率（**不归一化**，残差 = 背景占比） | 常开 |
| `_HoCryptomatteSelection` | RGBA8 ×4 | 具名选择 **8 层**：每张装两个 `(ID, 覆盖率)` 对（`R=id0, G=cov0, B=id1, A=cov1`） | 按需（有选择条目才分配；不够 8 个就少开几张） |
| `_HoCryptomatteFacing` | RGBA8 | **两个方向**：`RG = octahedral(forward)`、`BA = octahedral(side)`；消费端叉乘得第三轴 | 按需（有物体提供 faceBone 才分配） |
| 组表 / 条目表 / 选择表 | StructuredBuffer | 名字 ↔ ID、类别、标签、属性（AOV manifest 的来源） | 常开（小） |
| 内部 depth-stencil | 深度格式 | 两段式占用判定 + tie-break | **不发布** |

**不变式**（沿用 CB 那套，已在代码里）：ID 点采样 + `round(v*255)` 还原、不滤波不平均；覆盖率线性、只能按 ID 匹配加权；`K = N = 4` 无损；背景不占层。

## 4. 边界（三者并列、禁止互读）

| feature | 回答什么 | 输出 |
| --- | --- | --- |
| GB | 几何在哪、朝向如何、几何覆盖多少 | **几何法线** / depth / 几何覆盖率 / 描边 / sky |
| **本 feature** | **这是谁、占多少、抠哪一块** | ID / 覆盖率 / 具名选择 / 朝向（+ 以后登记进来的杂项 RT） |
| SB | 表面是什么样 | 表面色 / **着色法线** / roughness / metallic / thickness / … |

- **不发深度、不发几何/着色法线、不发表面数值**（各归各家）。
- **遮罩只有一个来源**：任何 feature 都不许自己再攒一套语义图。
- "效果该怎么用它"仍是**材质轻量参数**（管线草案 §6.3），不是这里的通道。

## 6. 待定

1. **组件与表的名字**：组件叫 `HoCryptomatteGroup`（沿用 Group 词）还是别的？组表 / 条目表 / 选择表三张 StructuredBuffer 的命名与行宽。（ID 空间、覆盖范围、选择层数、朝向内容**都已定**：见决策 8-11。）
2. **palette 是否保持两级**：现在"组 → 条目"仍然有用（`组 8 + 槽位 8` 的稀疏 ID 要映射到稠密行、组级标签、朝向挂在组上），但也有人会问"既然不分角色/场景，能不能一张平表"。**保持两级**（理由：稀疏→稠密的映射 + 组级语义），但把"组"这个词的含义在 UI 上讲清楚（一个角色、一组道具、一片场景区域都行）。
3. **合规导出档位是否 v1 就做**：① Deep IDs 风格的 UINT 通道（便宜）；② 真正合规的 `crypto_*`（float 位重解释 + manifest，Nuke 原生节点可直接点选，工作量大）。
4. **同组比较的语义**：ID 高字节仍是"组"，所以"同一组"可以廉价比较（发影 / 眼透要用）；但**组的边界由谁定**要写进组件文档（例如：同一个角色的所有部件同组 vs 同一片场景区域同组），否则艺术家会拿它当"任意分组"用。
