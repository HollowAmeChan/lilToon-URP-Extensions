# 旧仓库继续推进边界

> 本目录记录 `lilToon-URP-Extensions` 继续作为主推进仓库后的架构边界。`HoUrp-Extensions` 的厚包装不再作为当前主线，已完成的语义、资源、Debug、ImageChain 思想只作为可拆回旧仓库的参考。

---

## 0. 当前决策

当前不继续推进 `D:\Unity_Fork\HoUrp-Extensions` 的厚契约包装，主线回到：

```text
D:\Unity_Fork\lilToon-URP-Extensions
```

原因不是新方向错误，而是新仓库把“显式化”过度等同于中心注册表、总契约、总 Debug、总文档，导致实际开发、调试和迁移推进成本过高。

旧仓库当前已经有真实能力、真实材质接入、真实渲染顺序和真实问题现场。后续应在旧仓库里直接重整组分，而不是先把所有东西搬进新仓库再包装。

## 1. 新口径：薄显式化

显式化不等于所有信息都进中心注册表。

当前阶段采用：

```text
空间 + 命名 + 局部 descriptor + review = 显式声明
```

只有以下内容需要强注册或强契约：

- 跨 Feature 消费的资源。
- 跨 Domain 复用的语义。
- shader 公共 ABI。
- RenderGraph 生命周期需要被其它 pass 读取的资源。
- 会影响材质生成或材质接入的 pass 名、属性名、include。
- 需要出现在统一调试面板或 tile 视图里的 debug view。

以下内容不需要进入中心注册表：

- Feature 内部临时 RT。
- Feature 私有 debug pass。
- 单个效果内部的 pass 顺序。
- 只用于当前 effect 的 shader 参数。
- 只在当前帧当前链路内使用的 ImageChain 工作纹理。

用户侧仍需要一份明确的使用文档，但它应描述“Renderer Data 里加什么、按什么顺序、对象在哪里标记、debug 怎么看”，而不是把所有内部契约都提升为中心注册表。具体见 `07-用户向RendererFeature使用与顺序.md`。

## 2. HoAOV 重整方向

旧 `HoAOV` 不继续作为万能黑箱扩张，而是按职责拆成：

```text
MaterialBuffer = Material / Mask / Metadata Buffer
GeometryBuffer = Geometry / Deferred Buffer
```

### MaterialBuffer

保留和收拢对象、材质、mask、metadata：

- object id / group id
- object flags
- object custom / character part bits
- material class
- material profile
- thickness / curvature
- material custom channels
- 可复用的 diffuse / base / subsurface color 输入

### GeometryBuffer

收拢几何和未来延迟路径输入：

- depth
- normal
- motion / velocity
- future deferred scene material inputs

GeometryBuffer 也不能为了“以后也许有用”输出所有几何派生量。只有已经有真实消费者、或下一阶段明确要接入的资源才输出。

长期目标可以允许：

- 场景走 GeometryBuffer / deferred。
- 角色继续 forward。
- screen-space feature 同时消费 MaterialBuffer 和 GeometryBuffer。

禁止继续把以下资源塞进 AOV：

- SSS diffusion / blur / composite runtime texture。
- ShadowCast atlas / slice / receiver state。
- OIT accumulation / revealage。
- Shoost/ImageProcess 工作纹理。
- Debug tile / debug atlas / debug mode 状态。
- ShadowCast atlas / light data / receiver attenuation。

## 2.1 HoAOV 通道瘦身原则

当前 HoAOV 里有一些通道更像早期实验遗留，而不是稳定公共输入。后续不应继续默认输出：

- 切线法线：如果没有明确的 screen-space 消费者，不进入默认 GeometryBuffer。
- 整体遮罩 / 总 mask：如果具体消费者只需要 object id、part bit、material class 或 feature flag，就不要先输出一个总遮罩再二次解释。
- 预留 custom 通道：没有明确命名、范围、编码和消费者的 reserved/custom 不输出。
- 只为了 debug 方便存在的通道：归 debug feature 局部生成，不进入 MaterialBuffer/GeometryBuffer。
- 某个 effect 的运行时中间量：归该 effect 自己，不进入 HoAOV。

原则：

```text
没有真实消费者，就不输出。
消费者需要什么语义，就直接输出什么语义。
不要先输出宽泛通道，再让真实消费者多加一层 decode / remap。
```

允许保留的第一批 MaterialBuffer/GeometryBuffer 输出应以当前真实消费为准：

- object id / group id / flags。
- character part / object custom bits，但只保留已命名位。
- material class / profile / thickness / curvature。
- depth / normal。
- SSS 或 ScreenProcess 确实直接消费的 diffuse / subsurface source。

每删一个旧通道，需要同时检查：

- shader include 是否还写它。
- RenderFeature 是否还分配它。
- debug view 是否还显示它。
- HoPost/ImageProcess/SSS/CharacterSpecialization 是否真的读取它。
- 文档或 UI 是否还把它暴露成用户概念。

## 2.2 未来效果反推 Buffer 内容

两个 Buffer 不能只按当前 HoAOV 的旧 MRT 来裁剪，也要按未来明确想做的效果反推需要哪些通用输入。

已知未来方向包括：

- SSS / skin diffusion。
- 丁达尔效应。
- 大气散射。
- 体积雾。
- 水体 / 湿润表面。
- 屏幕空间角色与场景合成。
- 场景 deferred，角色 forward。

这些效果会共同需要一些“表面本身是什么”的输入。旧 HoAOV 里叫 `SssSource` 的东西，本质不应该叫 SSS source；它就是可复用的 surface diffuse / base color / subsurface color 输入。SSS 会用它，丁达尔、大气、体积雾、透射、湿润表面和屏幕空间合成以后也可能用它。

因此：

```text
旧 Aov.SssSource.rgb -> MaterialBuffer.Diffuse.rgb 或 MaterialBuffer.SurfaceColor.rgb
旧 Aov.SssSource.a   -> 不默认等于 SSS weight，是否保留要看真实通用语义
```

如果 alpha 表达的是材质本身的 participation / opacity / density，可以成为通用语义；如果 alpha 表达的是 SSS 运行时权重，就应由 SSS 自己维护。

### MaterialBuffer 第一批候选

面向未来消费者，MaterialBuffer 可以规划以下通用项：

- `SurfaceColor` / `DiffuseColor`：表面基础散射颜色，供 SSS、体积雾、大气、丁达尔、湿润表面等复用。
- `SubsurfaceColor`：如果和 diffuse 明确不同，作为更窄的材质散射颜色。
- `MaterialClass`：skin、hair、cloth、water、metal、glass、foliage 等粗分类。
- `MaterialProfile`：profile id，例如 SSS profile、fog interaction profile、water profile。
- `Thickness`：薄物体、皮肤、叶片、布料、半透明材质的近似厚度。
- `Curvature`：SSS、边缘透射、局部散射、风格化边缘的通用输入。
- `RoughnessLike` / `SmoothnessLike`：如果未来 screen-space wetness、atmospheric highlight、deferred scene 需要，再纳入；当前没有消费者就不默认输出。
- `TransmittanceHint`：如果丁达尔、体积雾或透射需要区分可透光表面，可以作为命名语义加入，不用挤进 custom。
- `EmissionHint`：如果体积/大气需要识别发光表面影响，可规划但不默认输出。

### GeometryBuffer 第一批候选

GeometryBuffer 面向屏幕空间几何关系：

- `Depth`：所有 screen-space effect 的基础。
- `Normal`：SSS、outline、fog、deferred scene lighting、edge-aware blur。
- `Motion`：temporal、motion trail、TAA、体积重投影。
- `SceneDepthClass` / `Coverage`：如果未来需要区分角色/场景/透明覆盖，再显式加入。

暂不默认输出：

- tangent normal：除非明确有各向异性、切线空间滤波或特殊材质消费者。
- packed all-mask：除非有多个消费者直接以同一编码读取。
- reserved vector：没有命名就不输出。

### 规划规则

每个候选项要先回答：

- 未来哪个效果会读？
- 它是材质/表面语义，还是几何语义？
- 它是通用输入，还是某个 feature 的 runtime 中间量？
- 它是否需要每个对象都输出？
- 它能否由现有 URP texture 或 renderer data 获得？
- 它是否值得占一个默认 MRT 通道？

结论不明确的，不进入默认 Buffer，可以先进 effect 私有路径或 debug 原型。

## 3. 后处理命名与边界

旧命名只保留为 legacy reference。文档、新规划和新增代码按新语义命名：

```text
HoPost / HoPostProcessing             -> ScreenProcess
Shoost / ShoostStack / ShoostPost     -> ImageProcess
```

这不是别名偏好，而是迁移方向。后续新增文档标题、局部 descriptor、review 清单和新抽象不再使用 `HoPost` / `ShoostStack` 作为概念名。

### ScreenProcess

语义感知屏幕处理，允许读取：

- MaterialBuffer
- GeometryBuffer
- depth / normal
- object id / material id / flags
- character part / region bits

典型用途：

- outline
- edge light
- drop shadow
- depth of field with semantic gate
- post lighting
- character/object/material targeted composite

### ImageProcess

最终图像处理链，默认只处理当前 image：

```text
ImageChain.Read -> pass -> ImageChain.Write -> swap
```

典型用途：

- color grading
- CRT / VHS
- grain
- vignette
- pixelize
- sharpen
- simple blur
- logo / frame / camera style effects

ImageProcess 不保留 AOV composite、semantic image pass 或 mask 输入例外。只要 effect 需要 mask、MaterialBuffer、GeometryBuffer、depth/normal、object id、ShadowCast 或其它额外语义输入，就迁到 ScreenProcess。
ImageProcess layer 顺序按用户栈执行，不再由 descriptor 或固定 effect order 强制重排。

## 4. Debug 新边界

Debug 不再作为一个中心大 Feature 统管所有 feature。

每个 feature 自己负责：

- 自己有哪些 debug view。
- debug view 的短命名。
- debug shader 或 shader pass。
- debug shader 所在目录。
- debug shader collection 的局部收集入口。
- 如何从自己的资源 decode。
- 是否需要 tile 显示。

公共层只负责：

- 根据 feature 提供的局部定义生成 enum / menu。
- 统一 tile view 布局。
- tile 上绘制短命名。
- 提供 replace / overlay / channel inspect 等基础显示模式。

这意味着 `HoAovDebug`、`HoSSSDebug`、`HoShadowCastDebug`、`ImageProcessAovDebug` 都可以保留局部归属。公共 debug UI 只能观察和编排它们，不能把所有资源都重新定义成一个中心 DebugDomain。
debug shader 和 debug view descriptor 必须跟随 feature 目录，例如 `Runtime/<Feature>/Shaders/Debug/` 与 `Runtime/<Feature>/<Feature>DebugViewInfo.cs`。
公共层可以生成 enum / menu / tile view，但不能把 shader、material、collector 搬到 `Runtime/Debug` 或 `Editor/Debug` 这类中心目录。

---

## 5. Debug shader 编译边界

很多 debug shader 比主功能还重，不能默认参与普通用户工程编译。

后续规则：

- 默认包只编译运行必需 shader。
- 重 debug shader 必须由用户显式打开 debug 功能后才进入编译或加载路径。
- Debug-only shader 不应被 runtime feature 默认 `Shader.Find` 强依赖。
- Debug shader 应拆到 feature 自己的 debug 目录，并通过局部 editor 工具或可选 shader collection 进入构建。
- Feature 的 debug 开关应区分“运行时显示 debug”和“项目启用 debug shader 编译/收集”。

推荐命名：

```text
Runtime/<Feature>/Shaders/
Runtime/<Feature>/Shaders/Debug/
Editor/<Feature>/Debug/
```

可选策略：

- `Resources` / `ShaderVariantCollection` 只在 debug package 或 debug profile 中引用。
- 使用 editor menu 生成 debug shader collection。
- 使用 scripting define 或 package sample 控制 debug shader inclusion。
- debug material lazy-load，且缺失时只降级提示，不阻断主 feature。

## 6. ImageProcess RDG 底线

旧 ShoostStack 是当前最重的后处理系统，但新语义名是 ImageProcess，必须 RDG 化。

底线：

- 所有额外 RT 都必须是 RenderGraph 临时资源。
- 不再为每个 layer 默认创建长期 RT。
- 不再让 effect 私自维护跨帧外部 RT，除非声明为 history / persistent。
- 读 camera color 再写 camera color 必须先 copy source，不能直接读写同一 active target。
- 纯 image pass 默认走统一 ImageChain 双缓冲。
- 多 pass effect 只能申请自己需要的局部临时 RDG 资源。
- ImageProcess 不读取 MaterialBuffer / GeometryBuffer / ShadowCast / SSS / OIT / CharacterSpecialization 等管线语义资源。

现有 `ImageProcessPass.RecordSinglePassLayer()` 这类“每层创建 destination”的做法可以作为过渡，但不是长期目标。长期应让普通单 pass 只使用 ImageChain 的 `WorkA/WorkB`。

允许脱离 ImageChain 双缓冲的情况：

- bloom / glow 需要 pyramid。
- iris blur / rgb blur 需要局部 ping-pong。
- motion trail / temporal 需要 history。
- logo / particle / weather 需要额外 texture 输入。

这些例外必须在 effect 局部 descriptor 中标注资源需求。
如果额外输入来自管线语义资源，则不属于 ImageProcess 例外，必须迁到 ScreenProcess。

## 7. 从新仓库可拆回旧仓库的东西

可以拿：

- `ImageChain` 的思想。
- `PostEffectDescriptor` / effect metadata 的轻量形式。
- `ShadowCast` 的灯光自动化填入和 atlas 规划经验。
- 独立 debug shader 测试思路。
- debug enum/menu/tile view 自动生成思路。
- debug tile 短命名显示。
- RDG 资源生命周期约束。

ShadowCast 自身改造见 `06-ShadowCast改造计划.md`。它归 Lighting/Shadow 组分，不进入 MaterialBuffer/GeometryBuffer，也不属于 ImageProcess。
用户向 RendererFeature 顺序、配置入口和 debug 使用见 `07-用户向RendererFeature使用与顺序.md`。
两个 post 系统的用户顺序和输入边界见 `08-PostProcess顺序与输入边界.md`。

不要拿：

- 中心大注册表。
- 总 DebugFeature 拥有所有 view。
- 每个语义都强制进入全局契约。
- 所有文档先行、代码后行的重流程。
- 为了“架构正确”给旧仓库再套一层厚 adapter。

## 8. 新增组分 review 清单

每次加新 feature 或迁移旧 feature，先回答：

- 它属于 `MaterialBuffer`、`GeometryBuffer`、`ScreenProcess`、`ImageProcess`、`Lighting`、`SSS`、`OIT`、`CharacterComposite` 还是其它明确组分？
- 它生产的资源是否会被其它 feature 消费？
- 它是否需要公共 shader ABI？
- 它的临时 RT 是否完全由 RDG 管理？
- 它是否读写 camera color？如果是，是否显式 copy？
- 它的 debug shader 是否默认编译？如果是，是否真的必要？
- 它的 debug view 短命名是什么？
- 它是否需要 tile view？
- 它是否只是局部实现细节，却被错误提升成公共契约？

如果一个答案不清楚，先改名字和目录，不要先加注册表。

## 9. 2026-05-25 当前大块状态

已基本完成：
- `ImageProcess` 已回到最终图像链职责：用户 layer 顺序即执行顺序，旧 AOV mask / Shoost 概念入口已清理，后续只剩 per-effect 参数尾巴。
- `ShadowCast` 已作为 Lighting/Shadow 组分独立，RendererFeature 自动收集可见投影灯，debug shader 为 feature-local 按需路径。
- `MetadataBuffer` / `GeometryBuffer` 已拆成独立 RendererFeature，旧 AOV 代码目录已删除，debug mode 和采样 helper 已逐步迁入各自 feature。

仍是主线大块：
- `MetadataBuffer` 的对象/材质语义纹理仍保留 `_lilHoAov*` 兼容 ABI，后续需要按 `MaskId`、`SurfaceData`、`MaterialCustom`、`ObjectCustom`、`SurfaceColor` 分批改成 MetadataBuffer 命名，并给旧材质 pass 留明确 alias 期。
- `MetadataBuffer` 输出 pass 仍临时绑定私有 normal/depth attachment 以维持旧 `HoAOV` MRT shader target 索引；最终应拆成 metadata-only shader target，normal/depth 只由 `GeometryBuffer` 公开输出。
- `HoAOV` / `HoAOVSSS` LightMode 仍是材质 ABI 的兼容层；后续需要补 MetadataBuffer/SurfaceColor/GeometryBuffer 原生 pass 后再移除。
- `ScreenProcess`、`SSS`、`CharacterSpecialization` 已按职责读取 MetadataBuffer / GeometryBuffer，但 shader 侧还需要继续把对象/材质语义采样名从旧 AOV 兼容名迁走。

本轮已开始处理 GeometryBuffer 公开 ABI：normal/depth 公开纹理名切到 `_HoGeometryBufferNormalDepthTexture` / `_HoGeometryBufferDepthTexture`，GeometryBuffer feature 同时发布旧 `_lilHoAov*` alias，供尚未迁移的旧 shader/material pass 过渡。
